# Требования к системе отслеживания свиней

## Введение

Система для автоматического подсчета свиней при прохождении через весы с возможностью сверки с ручными записями Excel. Система состоит из консольного приложения для обработки видео, базы данных для хранения результатов, модулей экспорта и сверки с Excel, и опционального веб-интерфейса для мониторинга.

## Глоссарий

- **Система** - Система отслеживания свиней (Pig Tracking System)
- **Консольное приложение** - Приложение командной строки для обработки видео
- **Акт взвешивания** - Событие прохождения группы свиней (3 или более) через весы
- **Проход** - Пересечение одной свиньей вертикальной линии детекции
- **База данных** - Локальная база данных Supabase (PostgreSQL)
- **YOLO модель** - Модель машинного обучения для детекции и сегментации свиней
- **Трекер** - Компонент для отслеживания свиней между кадрами с уникальными ID
- **Линия детекции** - Вертикальная линия на видео для подсчета проходов
- **Excel шаблон** - Файл Excel с ручными записями операторов
- **Сверка** - Процесс сравнения автоматических результатов с ручными записями
- **Cooldown** - Минимальный интервал времени между проходами одной свиньи

## Требования

### Требование 1: Обработка видеофайлов

**Пользовательская история:** Как оператор системы, я хочу обрабатывать видеофайлы для автоматического обнаружения актов взвешивания, чтобы избежать ручного подсчета свиней.

#### Критерии приемки

1. WHEN Консольное приложение запускается с параметром --video, THE Система SHALL загрузить указанный видеофайл и начать обработку кадров.

2. WHILE Система обрабатывает видеофайл, THE Система SHALL отображать прогресс обработки в консоли с указанием процента выполнения и количества обработанных кадров.

3. THE Система SHALL обнаруживать свиней на каждом кадре видео с использованием YOLO модели сегментации с порогом уверенности не менее 0.30.

4. THE Система SHALL присваивать уникальные идентификаторы каждой обнаруженной свинье и отслеживать их между кадрами с использованием Трекера.

5. WHEN свинья пересекает вертикальную линию детекции, THE Система SHALL зарегистрировать проход с указанием направления (слева или справа), временной метки и координат.

### Требование 2: Обнаружение актов взвешивания

**Пользовательская история:** Как оператор системы, я хочу автоматически определять начало и конец актов взвешивания, чтобы группировать проходы свиней в осмысленные события.

#### Критерии приемки

1. WHEN количество проходов достигает 3 или более за короткий период времени, THE Система SHALL начать новый акт взвешивания с записью временной метки начала.

2. WHILE акт взвешивания активен, THE Система SHALL накапливать статистику проходов слева и справа, пиковое количество свиней и общее количество уникальных свиней.

3. WHEN интервал без активности превышает 30 секунд, THE Система SHALL завершить текущий акт взвешивания с записью временной метки окончания.

4. IF количество проходов в группе меньше 3, THEN THE Система SHALL игнорировать эти проходы и не создавать акт взвешивания.

5. THE Система SHALL вычислять длительность каждого акта взвешивания как разницу между временем окончания и временем начала в секундах.

### Требование 3: Хранение данных в базе

**Пользовательская история:** Как оператор системы, я хочу сохранять результаты обработки в базе данных, чтобы иметь возможность анализировать исторические данные и экспортировать отчеты.

#### Критерии приемки

1. THE Система SHALL подключаться к локальной базе данных Supabase через параметры SUPABASE_URL и SUPABASE_KEY из конфигурации.

2. WHEN акт взвешивания завершается, THE Система SHALL сохранить запись в таблицу weighing_acts с полями: started_at, ended_at, duration_sec, left_count, right_count, peak_count, stream_id, video_file.

3. WHEN свинья пересекает линию детекции, THE Система SHALL сохранить запись в таблицу crossings с полями: act_id, pig_id, direction, crossed_at, line_x, line_y.

4. IF подключение к базе данных недоступно, THEN THE Система SHALL логировать ошибку и продолжить обработку без сохранения данных.

5. THE Система SHALL создавать необходимые таблицы автоматически при первом запуске с использованием SQL миграций.

### Требование 4: Экспорт результатов в Excel

**Пользовательская история:** Как оператор системы, я хочу экспортировать результаты обработки в формат Excel, чтобы делиться отчетами с коллегами и руководством в привычном формате.

#### Критерии приемки

1. THE Система SHALL анализировать структуру Excel шаблона из файла docs/Замеры 20.07 по 03.09.xlsx для определения формата столбцов и стилей.

2. WHEN пользователь запрашивает экспорт за период, THE Система SHALL получить акты взвешивания из базы данных за указанный период времени.

3. THE Система SHALL группировать акты взвешивания по дате и суммировать показатели (количество проходов, общий вес, средний вес) для каждого дня.

4. THE Система SHALL создавать Excel файл с той же структурой столбцов, форматированием и стилями, что и в исходном шаблоне.

5. THE Система SHALL сохранять экспортированный файл в указанную директорию с именем, содержащим дату экспорта.

### Требование 5: Сверка с ручными записями

**Пользовательская история:** Как оператор системы, я хочу сравнивать автоматические результаты с ручными записями операторов, чтобы оценить точность системы и выявить расхождения.

#### Критерии приемки

1. WHEN пользователь запускает режим сверки с параметром --excel-reference, THE Система SHALL загрузить ручные записи из указанного Excel файла.

2. THE Система SHALL сопоставлять автоматические акты взвешивания с ручными записями по дате с допуском плюс-минус 5 минут.

3. THE Система SHALL сравнивать количество проходов и вес между автоматическими и ручными записями для каждого сопоставленного акта.

4. THE Система SHALL вычислять метрики точности: Recall (полнота), Precision (точность), MAE (средняя абсолютная ошибка), MAPE (средняя процентная ошибка), корреляция Пирсона.

5. THE Система SHALL генерировать Excel отчет с четырьмя листами: совпадения (зеленый), расхождения (желтый/красный), пропущенные автоматически (серый), метрики точности.

6. THE Система SHALL сохранять отчет сверки в директорию test_results с именем, содержащим дату и время выполнения.

### Требование 6: Предотвращение двойного подсчета

**Пользовательская история:** Как оператор системы, я хочу избежать двойного подсчета одной и той же свиньи, чтобы получать точные результаты.

#### Критерии приемки

1. THE Система SHALL применять cooldown период длительностью 1.0 секунды между последовательными проходами одной свиньи через одну и ту же линию детекции.

2. WHEN свинья пересекает линию детекции повторно в течение cooldown периода, THE Система SHALL игнорировать это пересечение и не увеличивать счетчик проходов.

3. THE Система SHALL использовать уникальные идентификаторы треков для различения разных свиней на протяжении всего видео.

4. THE Система SHALL определять направление прохода (слева направо или справа налево) на основе изменения X-координаты центроида свиньи между кадрами.

5. THE Система SHALL интерполировать Y-координату свиньи в точке пересечения линии детекции для точного определения позиции прохода.

### Требование 7: Тестовый режим работы

**Пользовательская история:** Как разработчик системы, я хочу запускать автоматическое тестирование на видеофайлах с известными результатами, чтобы оценивать точность алгоритмов.

#### Критерии приемки

1. WHEN Консольное приложение запускается с параметром --mode test, THE Система SHALL активировать тестовый режим с автоматической сверкой результатов.

2. THE Система SHALL обрабатывать указанный видеофайл полностью от начала до конца с сохранением всех обнаруженных актов в базу данных.

3. WHEN обработка видео завершается в тестовом режиме, THE Система SHALL автоматически запустить сверку результатов с Excel файлом, указанным в параметре --excel-reference.

4. THE Система SHALL выводить метрики точности в консоль: Recall, Precision, F1-score, MAE, MAPE, корреляция Пирсона.

5. THE Система SHALL сохранять результаты тестирования в директорию, указанную в параметре --output, включая отчет сверки и JSON файл с метриками.

### Требование 8: Конфигурируемость параметров (опционально)

**Пользовательская история:** Как администратор системы, я хочу настраивать параметры обработки без изменения кода, чтобы адаптировать систему под разные условия съемки.

#### Критерии приемки

1. THE Система SHALL загружать параметры конфигурации из файла .env при запуске, включая пороги детекции, позиции линий и параметры актов.

2. WHERE параметр CONF_THRESHOLD указан в конфигурации, THE Система SHALL использовать это значение как минимальный порог уверенности для детекции свиней.

3. WHERE параметры LINE_LEFT_X и LINE_RIGHT_X указаны в конфигурации, THE Система SHALL использовать эти значения для позиционирования вертикальных линий детекции.

4. WHERE параметры MIN_PIGS_FOR_ACT и MAX_INTERVAL_SEC указаны в конфигурации, THE Система SHALL использовать эти значения для определения начала и конца актов взвешивания.

5. THE Система SHALL автоматически определять оптимальное устройство для инференса (CUDA GPU или CPU) на основе доступного оборудования.

### Требование 9: Веб-интерфейс для мониторинга (опционально)

**Пользовательская история:** Как оператор системы, я хочу просматривать текущие показатели и историю актов через веб-интерфейс, чтобы мониторить работу системы удаленно с мобильного устройства.

#### Критерии приемки

1. THE Система SHALL предоставлять REST API эндпоинт GET /api/weighing/acts для получения списка актов взвешивания за указанный период.

2. THE Система SHALL предоставлять REST API эндпоинт GET /api/weighing/stats для получения текущей статистики: количество свиней, проходы слева/справа, активный акт.

3. THE Система SHALL предоставлять REST API эндпоинт POST /api/weighing/export для экспорта актов в Excel файл с возможностью скачивания.

4. THE Система SHALL предоставлять веб-страницу с адаптивным дизайном для отображения показателей на мобильных устройствах.

5. WHILE веб-страница открыта, THE Система SHALL обновлять отображаемые данные автоматически каждые 5 секунд.
