# Документ требований

## Введение

Эта функция представляет собой двухкомпонентную систему для отслеживания и взвешивания свиней при прохождении через весы. Система состоит из:

1. Консольного приложения для работы в фоновом режиме, которое выполняет инференс в реальном времени с камеры или видео и записывает события прохождения свиней для последующей сверки с записями Excel
2. Веб-интерфейса, оптимизированного для мобильных устройств, который отображает прямую трансляцию с камеры или предзагруженные видео из папки uploads, показывая количество свиней, направление прохода (слева/справа) и статистику по весу (общий и средний)

Основной приоритет - стабильная работа в фоновом режиме и точный подсчет свиней, проходящих через весы.

## Требования

### Требование 1: Консольное приложение для инференса и журналирования в фоновом режиме

**Пользовательская история:** Как оператор фермы, я хочу консольное приложение, которое работает в фоне и обрабатывает видеопотоки с камеры/видео для обнаружения и записи проходов свиней, чтобы я мог сверить автоматический подсчет с моими записями в Excel.

#### Критерии приемки

1. КОГДА консольное приложение запускается, ТО оно ДОЛЖНО загрузить модель YOLO и инициализировать источник видео (камера или видеофайл)
2. КОГДА источник видео настроен, ТО система ДОЛЖНА поддерживать как прямые трансляции с камеры, так и видеофайлы в качестве входных данных
3. КОГДА приложение обрабатывает кадры, ТО оно ДОЛЖНО обнаруживать свиней, используя существующую модель сегментации YOLO
4. КОГДА свиньи пересекают линию детекции, ТО система ДОЛЖНА записывать события прохода с временной меткой, направлением, количеством и оценкой веса
5. КОГДА события прохода записываются, ТО система ДОЛЖНА записывать их в структурированный формат лог-файла, совместимый с проверкой в Excel
6. КОГДА приложение работает, ТО оно ДОЛЖНО работать непрерывно в фоновом режиме без необходимости взаимодействия с пользователем
7. КОГДА возникают ошибки, ТО система ДОЛЖНА записывать ошибки в лог и продолжать обработку без сбоев
8. ЕСЛИ источник видео заканчивается, ТО система ДОЛЖНА либо зациклить воспроизведение (для видеофайлов), либо переподключиться (для потоков с камеры)
9. КОГДА запускается обработка большого видеофайла, ТО система ДОЛЖНА прогнать все видео и автоматически обнаружить все акты взвешивания (всплески активности при прохождении вертикальных линий отсечки)
10. КОГДА обнаружен акт взвешивания, ТО система ДОЛЖНА записать его как отдельное событие с началом, концом, пиковым количеством свиней и общей статистикой
11. КОГДА обрабатывается длинное видео, ТО система ДОЛЖНА показывать прогресс обработки (процент, текущее время видео, количество обнаруженных актов)

### Требование 2: Мобильный веб-интерфейс для мониторинга в реальном времени

**Пользовательская история:** Как оператор фермы, использующий мобильное устройство, я хочу простой веб-интерфейс, который показывает мне видео с камеры или загруженное видео с подсчетом свиней, направлениями прохода и статистикой по весу, чтобы я мог удаленно контролировать процесс взвешивания.

#### Критерии приемки

1. КОГДА я открываю веб-интерфейс на мобильном устройстве, ТО он ДОЛЖЕН отображать адаптивный макет, оптимизированный для мобильных экранов
2. КОГДА страница загружается, ТО она ДОЛЖНА показывать доступные источники видео (прямая трансляция с камеры или видео из папки uploads)
3. КОГДА я выбираю источник видео, ТО система ДОЛЖНА отображать видеопоток с наложениями детекции
4. КОГДА свиньи обнаружены, ТО интерфейс ДОЛЖЕН отображать текущее количество свиней в кадре
5. КОГДА свиньи пересекают линию детекции, ТО интерфейс ДОЛЖЕН показывать направление прохода (слева или справа) с визуальными индикаторами
6. КОГДА обнаружены проходы, ТО интерфейс ДОЛЖЕН отображать общий вес и средний вес на свинью
7. КОГДА интерфейс обновляет статистику, ТО он ДОЛЖЕН обновляться в реальном времени без перезагрузки страницы
8. КОГДА в папке uploads существует несколько видео, ТО интерфейс ДОЛЖЕН предоставлять простой селектор для переключения между ними

### Требование 3: Точное обнаружение и подсчет актов взвешивания (массовых проходов)

**Пользовательская история:** Как оператор фермы, я хочу, чтобы система фиксировала только акты взвешивания (массовые проходы свиней через весы), игнорируя одиночные случайные проходы, чтобы данные соответствовали реальным актам взвешивания.

#### Критерии приемки

1. КОГДА свинья входит в зону детекции, ТО система ДОЛЖНА отслеживать её с уникальным ID
2. КОГДА свинья пересекает линию детекции, ТО система ДОЛЖНА подсчитать её ровно один раз
3. КОГДА несколько свиней пересекают линию одновременно, ТО система ДОЛЖНА подсчитать каждую свинью индивидуально
4. КОГДА свинья движется туда-сюда, ТО система ДОЛЖНА подсчитывать только проходы, которые завершают полный переход
5. КОГДА определяется направление прохода, ТО система ДОЛЖНА точно классифицировать его как слева-направо или справа-налево
6. КОГДА отслеживаются свиньи, ТО система ДОЛЖНА поддерживать точность отслеживания даже при перекрытиях
7. КОГДА свиньи перекрываются, ТО система ДОЛЖНА использовать маски сегментации для разделения отдельных животных
8. ЕСЛИ отслеживание временно потеряно, ТО система ДОЛЖНА попытаться повторно идентифицировать ту же свинью, чтобы избежать двойного подсчета
9. КОГДА начинается массовый проход (настраиваемый порог, например 3+ свиньи за короткий период), ТО система ДОЛЖНА автоматически начать "акт взвешивания"
10. КОГДА активность падает ниже порога (например, нет проходов более 30 секунд), ТО система ДОЛЖНА автоматически завершить "акт взвешивания"
11. КОГДА система определяет акт взвешивания, ТО она ДОЛЖНА использовать настраиваемые пороги: минимальное количество свиней для начала акта, максимальный интервал между проходами для продолжения акта, минимальная длительность акта
12. КОГДА происходят одиночные проходы (ниже порога), ТО система ДОЛЖНА игнорировать их и НЕ сохранять в базу данных
13. КОГДА сохраняются данные, ТО в базу попадают ТОЛЬКО акты взвешивания с полной статистикой
14. КОГДА отображается статистика, ТО система ДОЛЖНА показывать только данные по актам взвешивания: количество актов, общее количество свиней в актах, средний размер акта

### Требование 4: Стабильная работа в фоновом режиме

**Пользовательская история:** Как оператор фермы, я хочу, чтобы система надежно работала в фоновом режиме в течение длительного времени, чтобы мне не нужно было постоянно контролировать или перезапускать её.

#### Критерии приемки

1. КОГДА консольное приложение работает, ТО оно ДОЛЖНО работать непрерывно не менее 24 часов без ручного вмешательства
2. КОГДА использование памяти увеличивается, ТО система ДОЛЖНА выполнять правильную очистку для предотвращения утечек памяти
3. КОГДА обрабатываются кадры, ТО система ДОЛЖНА поддерживать стабильную частоту кадров без деградации со временем
4. КОГДА возникают временные ошибки (проблемы с сетью, пропуски кадров), ТО система ДОЛЖНА восстанавливаться автоматически
5. КОГДА системные ресурсы ограничены, ТО приложение ДОЛЖНО адаптировать настройки качества для поддержания стабильности
6. КОГДА приложение запускается, ТО оно ДОЛЖНО записывать в лог информацию о запуске и конфигурации
7. КОГДА приложение работает, ТО оно ДОЛЖНО периодически записывать в лог состояние здоровья (обработанные кадры, использование памяти и т.д.)
8. ЕСЛИ возникает критическая ошибка, ТО система ДОЛЖНА попытаться автоматически перезапустить конвейер обработки видео

### Требование 5: Сохранение данных в PostgreSQL/Supabase и экспорт в Excel

**Пользовательская история:** Как оператор фермы, я хочу, чтобы все события прохода сохранялись в надежную базу данных (локальный PostgreSQL или локальный Supabase) и могли экспортироваться в Excel, чтобы я мог анализировать данные и сверять с моими записями.

#### Критерии приемки

1. КОГДА консольное приложение запускается, ТО оно ДОЛЖНО подключиться к базе данных (локальный PostgreSQL или локальный Supabase, параметры подключения из .env файла)
2. КОГДА происходит событие прохода, ТО система ДОЛЖНА сохранить его в таблицу `crossings` с полями: id, created_at, direction, pig_count, weights (JSONB), total_weight, avg_weight, stream_id
3. КОГДА завершается акт взвешивания, ТО система ДОЛЖНА сохранить его в таблицу `weighing_acts` с полями: id, started_at, ended_at, left_count, right_count, peak_count, total_weight, avg_weight, stream_id, video_file
4. КОГДА пользователь запрашивает экспорт, ТО система ДОЛЖНА создать Excel файл (.xlsx) из данных базы в формате, идентичном существующему шаблону `docs/Замеры 20.07 по 03.09.xlsx`
5. КОГДА создается Excel файл, ТО он ДОЛЖЕН содержать те же столбцы, порядок столбцов, форматирование и структуру, что и в файле `docs/Замеры 20.07 по 03.09.xlsx`
6. КОГДА я открываю экспортированный файл в Excel, ТО все столбцы ДОЛЖНЫ быть правильно отформатированы: даты в формате DD.MM.YYYY HH:MM, числа с правильными разделителями, текст в кодировке UTF-8
7. КОГДА система экспортирует данные, ТО она ДОЛЖНА проанализировать структуру файла `docs/Замеры 20.07 по 03.09.xlsx` и воспроизвести: названия столбцов, типы данных, ширину столбцов, стили ячеек
8. КОГДА выполняется сверка данных, ТО система ДОЛЖНА предоставить функцию сравнения экспортированного файла с существующими записями Excel, выделяя расхождения
9. КОГДА происходит ошибка подключения к базе данных, ТО система ДОЛЖНА записывать события в локальную очередь (SQLite) и синхронизировать при восстановлении соединения
10. КОГДА веб-интерфейс запрашивает данные, ТО он ДОЛЖЕН получать их из базы данных через REST API (напрямую из PostgreSQL или через Supabase REST API)
11. КОГДА используется Supabase, ТО веб-интерфейс МОЖЕТ использовать real-time подписки для мгновенного обновления показателей
12. КОГДА база данных растет, ТО система ДОЛЖНА поддерживать партиционирование таблиц по датам и архивацию старых данных
13. КОГДА система экспортирует данные, ТО она ДОЛЖНА использовать структуру и формат из файла-шаблона `docs/Замеры 20.07 по 03.09.xlsx` как эталон для совместимости
14. КОГДА приложение запускается первый раз, ТО оно ДОЛЖНО автоматически создать необходимые таблицы и индексы (миграции через SQL скрипты или Supabase CLI)
15. КОГДА используется локальный Supabase, ТО он ДОЛЖЕН запускаться через Docker Compose вместе с приложением для простоты развертывания

### Требование 6: Анализ формата Excel и функция сверки

**Пользовательская история:** Как оператор фермы, я хочу, чтобы система автоматически изучила формат моего Excel файла с записями и могла сверить автоматически обнаруженные данные с ручными записями, чтобы проверить точность системы.

#### Критерии приемки

1. КОГДА система запускается первый раз, ТО она ДОЛЖНА проанализировать файл-шаблон `docs/Замеры 20.07 по 03.09.xlsx` и извлечь:
   - Названия всех столбцов и их порядок
   - Типы данных в каждом столбце (дата, число, текст)
   - Форматы дат и чисел (разделители, количество знаков после запятой)
   - Ширину столбцов и стили ячеек (шрифт, выравнивание, границы)
   - Структуру данных (какие столбцы содержат временные метки, количество, вес и т.д.)
2. КОГДА система анализирует структуру Excel, ТО она ДОЛЖНА сохранить схему в конфигурационный файл (JSON) для последующего использования при экспорте
3. КОГДА я загружаю файл Excel с ручными записями для сверки, ТО система ДОЛЖНА прочитать его, используя извлеченную схему, и сопоставить с данными из базы по временным меткам
4. КОГДА выполняется сверка, ТО система ДОЛЖНА сравнить построчно: дату/время акта, количество проходов слева, количество проходов справа, общий вес, средний вес
5. КОГДА обнаружены расхождения, ТО система ДОЛЖНА создать отчет Excel с тремя листами:
   - "Совпадения" - акты, которые совпали (зеленый фон)
   - "Расхождения" - акты с различиями (желтый <10%, красный >10%)
   - "Пропущенные/Лишние" - акты, которые есть только в одном источнике
6. КОГДА создается отчет о сверке, ТО каждая строка с расхождением ДОЛЖНА показывать: значение из Excel, значение из системы, разницу в процентах
7. КОГДА выполняется сверка, ТО система ДОЛЖНА учитывать допустимую погрешность во времени (настраиваемая, по умолчанию ±5 минут) для сопоставления актов
8. КОГДА сверка завершена, ТО система ДОЛЖНА показать итоговую статистику: общее количество актов, процент совпадений, количество расхождений, средняя точность подсчета, средняя погрешность по весу
9. КОГДА обнаружено расхождение, ТО система ДОЛЖНА предоставить ссылку на соответствующий фрагмент видео (если доступен) для ручной проверки
10. КОГДА система экспортирует данные в Excel, ТО она ДОЛЖНА использовать сохраненную схему для точного воспроизведения формата исходного файла

### Требование 7: Тестовый режим для валидации точности системы

**Пользовательская история:** Как оператор фермы, я хочу запустить систему в тестовом режиме на видео за определенный период времени и автоматически сверить результаты с Excel файлом, который предоставят операторы, чтобы проверить точность системы перед внедрением.

#### Критерии приемки

1. КОГДА я запускаю систему в тестовом режиме, ТО я ДОЛЖЕН указать: видеофайл, период времени (начало и конец), путь к Excel файлу с эталонными данными
2. КОГДА система работает в тестовом режиме, ТО она ДОЛЖНА обработать видео в фоне без GUI, выводя только прогресс в консоль
3. КОГДА обработка завершена, ТО система ДОЛЖНА автоматически выполнить сверку с предоставленным Excel файлом
4. КОГДА выполняется сверка, ТО система ДОЛЖНА сопоставить акты взвешивания по временным меткам с допустимой погрешностью (настраиваемой)
5. КОГДА сверка завершена, ТО система ДОЛЖНА создать детальный отчет с метриками точности:
   - Процент правильно обнаруженных актов (Recall)
   - Процент ложных срабатываний (False Positives)
   - Средняя погрешность по количеству свиней (MAE, MAPE)
   - Средняя погрешность по весу (MAE, MAPE)
   - Корреляция между автоматическими и ручными подсчетами
6. КОГДА создается отчет, ТО он ДОЛЖЕН включать визуализацию: графики сравнения, таблицы расхождений, гистограммы ошибок
7. КОГДА обнаружены систематические ошибки, ТО система ДОЛЖНА предложить рекомендации по настройке параметров (пороги детекции, позиции линий и т.д.)
8. КОГДА тестовый режим завершен, ТО система ДОЛЖНА сохранить все результаты в папку `test_results/` с временной меткой для последующего анализа
9. КОГДА запускается несколько тестов, ТО система ДОЛЖНА позволять сравнить результаты разных запусков для отслеживания улучшений
10. КОГДА система работает в тестовом режиме, ТО она ДОЛЖНА логировать все промежуточные результаты для отладки (обнаруженные свиньи, проходы, акты)

### Требование 8: Пакетная обработка видео и автоматическое обнаружение актов взвешивания

**Пользовательская история:** Как оператор фермы, я хочу запустить консольное приложение на большом видеофайле и автоматически получить все акты взвешивания с полной статистикой, чтобы быстро обработать архивные записи.

#### Критерии приемки

1. КОГДА я запускаю приложение с видеофайлом, ТО оно ДОЛЖНО автоматически обработать весь файл от начала до конца
2. КОГДА обнаруживается всплеск активности (свиньи начинают проходить через линии), ТО система ДОЛЖНА автоматически начать новый акт взвешивания
3. КОГДА активность падает ниже порога, ТО система ДОЛЖНА автоматически завершить текущий акт взвешивания

### Требование 9: Веб-интерфейс без видео - только показатели

**Пользовательская история:** Как оператор фермы, использующий мобильное устройство, я хочу простой веб-интерфейс, который показывает только ключевые показатели без видеопотока, чтобы экономить трафик и ресурсы устройства.

#### Критерии приемки

1. КОГДА я открываю веб-интерфейс, ТО он ДОЛЖЕН отображать только текстовые показатели без видеопотока
2. КОГДА страница загружается, ТО она ДОЛЖНА показывать: текущее количество свиней, количество проходов слева, количество проходов справа, общий вес, средний вес
3. КОГДА происходят изменения в показателях, ТО интерфейс ДОЛЖЕН обновляться в реальном времени, получая данные из базы через API
4. КОГДА отображаются показатели, ТО они ДОЛЖНЫ быть крупными и читаемыми на мобильном экране
5. КОГДА доступно несколько источников видео, ТО интерфейс ДОЛЖЕН позволять выбрать источник для мониторинга показателей
6. КОГДА происходит проход свиньи, ТО интерфейс ДОЛЖЕН визуально выделить это событие (например, анимацией или изменением цвета)
7. КОГДА нет подключения к источнику, ТО интерфейс ДОЛЖЕН четко показывать статус "Нет подключения"
8. КОГДА пользователь хочет увидеть историю, ТО интерфейс ДОЛЖЕН показывать последние 10-20 событий прохода с временными метками из базы данных
9. КОГДА выбран видеофайл из папки uploads, ТО интерфейс ДОЛЖЕН показывать статистику по этому файлу из базы
10. КОГДА пользователь хочет экспортировать данные, ТО интерфейс ДОЛЖЕН предоставить кнопку для скачивания CSV файла с выбранным периодом
11. КОГДА отображается список актов взвешивания, ТО интерфейс ДОЛЖЕН показывать их в виде таблицы с возможностью фильтрации по дате
